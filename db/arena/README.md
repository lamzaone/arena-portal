# Arena group authority

This directory contains migrations for the **arena/game database**. It is a
separate migration stream from the portal migrations in `db/*.sql`.

Apply `001_group_authority.sql` to `GAME_DATABASE_URL`. Do not apply it to
`PORTAL_DATABASE_URL`. Apply `db/025_arena_group_commerce_bridge.sql` to the
portal database only. The two migrations create a foundation; they do not copy
legacy records, switch application readers, or delete an existing table.

## Ownership boundary

The arena database is the source of truth for identity and access:

| Arena-owned state | Purpose |
| --- | --- |
| `arena_scopes` | Stable global/server scope registry and mappings to an Admins.Core server GUID or VIPCore `sid`. |
| `arena_groups` | Canonical admin, VIP, and custom group definitions, presentation, permissions, perks, and stable UUIDs. |
| `arena_group_scopes` | The scopes in which a group exists plus explicit per-scope overrides. |
| `arena_group_memberships` | Canonical player membership, expiry, provenance, and optimistic `row_version`. |
| `arena_vip_subscriptions` | The single current VIP tier for each player, scope, and VIP family. |
| `arena_vip_subscription_history` | Immutable VIP activation, extension, upgrade, removal, conflict, and migration history. |
| command, receipt, and outbox tables | Idempotent writes and reliable propagation to portal-owned projections. |

The portal database remains the source of truth for commerce:

| Portal-owned state | Purpose |
| --- | --- |
| catalogue and group listings | Products, prices, sale windows, and the stable arena target of a product. |
| wallets, orders, and marketplace records | Payment and exchange history. |
| inventory and group rewards | Item instances and the rules that manufacture or revoke them. |
| `portal_membership_activation_jobs` | Durable cross-database activation sagas. |
| `portal_arena_membership_event_receipts` | Exactly-once portal handling of arena outbox events. |

There are deliberately no foreign keys between databases. In production the
portal and arena databases can be on different hosts, so a cross-database SQL
transaction would not be safe or portable.

## Servers and scopes

Use one highly available arena identity database and represent isolation with
logical scopes. Do not create a separate identity database per game server.
That keeps staff editing, conflict resolution, audit history, and commercial
VIP behavior understandable while still allowing a group or membership to be
server-specific.

The migration creates a deterministic `global` scope with UUID
`00000000-0000-0000-0000-000000000001` and the legacy VIPCore mapping
`vip_server_id = 0`. Portal-sold network VIP should normally target this
scope. Each real server gets another `server` scope, mapped to its Admins.Core
GUID, VIPCore `sid`, or both. A group is available in a scope only when an
`arena_group_scopes` row exists.

Admins.Core and VIPCore generate independent plugin-local GUIDs, so a
`vip_servers.GUID` value must never be copied into `admin_server_guid` or used
to infer that two scopes are the same. The portal's explicit
`GAME_SERVER_GUID` + `GAME_VIP_SERVER_ID` pair identifies the physical server.
Its canonical scope key is `server.<GAME_SERVER_GUID>`, and that one row carries
both native locators. Unconfigured servers remain single-locator scopes until
an explicit pairing is provided.

Do not infer that VIPCore scope `0` and scope `1` are interchangeable. Existing
installations may contain users under both values while definitions exist in
only one of them. The data migration must register each observed scope,
identify the intended definition set, and surface unresolved rows as conflicts
instead of silently moving or extending them.

## Stable identity and legacy compatibility

`arena_groups.group_uuid` is the durable cross-database identifier.
`group_key` is a stable human-readable key for configuration and diagnostics.
Both must remain unchanged when a display name, badge, permissions, tier order,
or price changes.

`legacy_portal_group_id` preserves the numeric portal group identity during
cutover. Existing portal `group_id` columns remain for compatibility, while
new listing, reward, catalogue-target, command, and event records carry the
arena UUID. A backfill must fail on ambiguous mappings; it must never guess by
display name alone.

UUIDs are generated by application or migration tooling, normalized to
lowercase, and validated before insert. A deterministic UUIDv5-style mapping
is recommended for repeatable legacy imports. The namespace and input format
must be recorded in the cutover runbook before generating production UUIDs.

## Canonical memberships and VIP state

`arena_group_memberships` holds one current row for a player, group, and scope.
Extensions and edits update that row, increment `row_version`, and append
history rather than adding another active copy. Provenance fields retain the
source system, actor, inventory item, and command.

VIP additionally uses `arena_vip_subscriptions` as the lock and current-state
row. Its primary key is `(steam_id, scope_id, vip_family_key)`, so at most one
tier can be current within that family and scope. A player may still hold
unrelated VIP families or intentionally different server-scoped memberships.
`legacy_suppressed_until` and `legacy_suppressed_permanently` explicitly keep
preserved `vip_users` rows from resurfacing while an imported canonical tier
or suppression-only tombstone owns that legacy interval. A future scheduled
subscription does not suppress legacy access before `starts_at`.
An expiry of `NULL` means permanent. Permanent access must not be shortened by
an item activation; the command should be rejected or recorded as an applied
no-op according to the product policy, while already-owned portal rewards stay
reconcilable through history and outbox events.

All VIP edits use the same command path, including staff add, remove, extend,
tier change, and inventory activation. The writer locks rows in this order:

1. `arena_membership_commands` for the command UUID or issuer request key.
2. `arena_vip_subscriptions` for player, scope, and family (`FOR UPDATE`).
3. The referenced membership row, if one exists.

Within that one arena transaction it updates canonical state, appends history,
stores a command receipt, and emits an outbox event. Readers must ignore
expired or non-`active` rows even before a cleanup worker changes their status.

## Price-derived VIP conversion

Pricing remains portal-owned. At activation preparation time, the portal reads
the current enabled tier prices and conversion rules, computes the proposed
duration change, and stores the complete rate schedule and algorithm version in
`rate_snapshot`. It hashes the canonical JSON into `rate_snapshot_hash` and
sets a short `rate_snapshot_expires_at`.

The arena command records the same snapshot and hash, and its history stores
the source duration, converted duration, and any time deducted from the current
subscription. This makes extensions and upgrades auditable while allowing
marketplace price differences to change for future activations. A retry always
uses the original snapshot; it must not recalculate under a newer price list.
An expired snapshot that has not yet been applied is rejected and prepared
again under a new command UUID. Once an arena receipt exists, expiry does not
invalidate the committed result.

Rejected attempts remain immutable. Their explicit inventory-reservation key
is cleared atomically with the durable rejection, which releases the item for
a newly priced job without editing or reusing either rejected receipt.
Prepared, ambiguous, manual-review,
applied, and completed attempts continue to reserve the item uniquely.

The conversion algorithm itself must be versioned in the snapshot. It should
operate on integer seconds and explicit integer price units, define rounding,
and reject zero or missing prices. The arena service validates the snapshot
shape, target group version, scope, and expected before-state before applying
the portal's proposed result. This avoids floating-point drift and prevents a
stale or forged portal request from turning a short high-tier item into an
unbounded upgrade.

## Activation saga

Membership activation spans two database hosts and therefore uses a saga. The
delivery guarantee is at least once; idempotent commands and receipts make the
observable effect exactly once.

### 1. Prepare in the portal database

In one portal transaction:

1. Lock the inventory item and require its owner and `state = 'available'`.
2. Resolve the enabled catalogue target and snapshot its arena group UUID,
   scope UUID, row version, duration, and current rate schedule.
3. Create or reuse the economy operation using the external idempotency key.
4. Insert one activation job with a new `job_uuid` and
   `arena_command_uuid`. The item ID, command UUID, operation ID, and
   idempotency key are independently unique. The request hash is indexed for
   conflict diagnostics but is not globally unique.
5. Change the item state to `activation_pending` and commit.

The request hash must cover the operation type, owner, item instance, target
group, scope, duration, group version, and rate-snapshot hash. Canonical field
ordering and the hash algorithm must be versioned. A reused idempotency key
with a different request hash is a conflict, not a retry.

### 2. Apply in the arena database

The worker sends the same command UUID until a durable receipt is returned.
The arena service:

1. Inserts or reloads `arena_membership_commands` by command UUID and
   `(issuer, issuer_request_key)`.
2. Rejects a mismatched request hash for either identity.
3. Locks canonical VIP state, validates scope/group/version/rates, and applies
   the add, extension, upgrade, removal, or explicit no-op.
4. Updates membership/subscription state and history.
5. Inserts `arena_membership_command_receipts` and an
   `arena_membership_outbox` event in the same transaction.

If the network fails after arena commit, the portal retries the identical
command and receives the stored receipt. It must never create a replacement
command just because a response was lost.

### 3. Finalize in the portal database

After an `applied` arena receipt, one portal transaction locks the job and
inventory item, verifies the receipt hash, consumes the `activation_pending`
item, records the operation result, and marks the job `completed`. A rejected
receipt returns the reserved item to `available` and records a deterministic
error. Portal group reward changes are handled idempotently from arena outbox
events, not by writing arena membership tables from portal code.

An unknown or timed-out arena result is not a rejection. Keep the item pending,
query the command receipt, and retry delivery. Release an item only after a
durable rejected receipt or a reviewed compensating decision. This is the key
invariant that prevents both a free membership and double consumption.

## Job states and recovery

| State | Meaning and next action |
| --- | --- |
| `prepared` | Item is reserved; command has not been leased. Dispatch it. |
| `dispatching` | A worker holds a short lease. Recover after a stale `locked_at`. |
| `retry_wait` | Delivery failed without a known arena outcome. Retry the same command after `available_at`. |
| `arena_applied` | A verified applied receipt is stored. Finalize portal inventory locally. |
| `finalizing` | A worker is performing the portal transaction. Recover idempotently after a stale lease. |
| `completed` | Arena effect and portal consumption are both durable. Terminal. |
| `rejected` | A durable rejected receipt was finalized and the item reservation was released. Terminal. |
| `manual_review` | Hash mismatch, impossible state, or exhausted automated recovery. Do not release or consume automatically. |

Workers claim rows with a bounded lease and increment `attempts`. Recovery
must inspect the arena receipt before changing an ambiguous job. Store receipt
and result JSON for diagnostics, but make decisions from validated status and
hash fields rather than trusting arbitrary JSON.

## Arena outbox and portal inventory reconciliation

Every membership mutation writes a uniquely keyed arena outbox event in the
same transaction as the mutation. A dispatcher may publish an event repeatedly
until the portal acknowledges it. The portal first inserts
`portal_arena_membership_event_receipts` by `arena_event_uuid`, then applies
inventory rewards, badges, and related portal projections in the same local
transaction. A duplicate event with the same UUID and a different payload hash
goes to manual review.

Mark the arena outbox row `published` only after the portal receipt is durable.
A `failed` outbox row means automated delivery needs attention; it does not
roll back the authoritative membership. Event payloads should include schema
version, group and scope UUIDs, membership UUID, Steam ID, status, expiry,
`row_version`, and the command UUID where relevant.

## Inventory state safety

Portal migration `025_arena_group_commerce_bridge.sql` appends
`activation_pending` to the existing inventory ENUM, preserving all prior
values and their ordinal positions. Do not start writing that value until all
application paths that sell, trade, attach, equip, revoke, or consume an item
have been reviewed to require `state = 'available'` where appropriate.

A pending item belongs to exactly one activation job and cannot be sold,
transferred, equipped, attached, or activated again. Administrative recovery
must operate through the job and command receipt, not by editing the item state
alone.

## Suggested cutover sequence

1. Back up both databases and record schema/version metadata.
2. Apply `db/arena/001_group_authority.sql` to the arena database.
3. Apply `db/025_arena_group_commerce_bridge.sql` to the portal database.
4. Run the deterministic backfill preflight from `arena-portal`:

   ```powershell
   node --env-file=.env.local scripts/migrate-arena-group-authority.mjs
   ```

   It is read-only unless `--apply` is present. Resolve every reported schema,
   mapping, or collision blocker and compare source/effective counts before
   continuing.
5. Stop Admins.Core, VIPCore, portal membership, and inventory-activation
   writers, take fresh backups, then run the same command with `--apply`.
   Arena rows commit before portal bridge projections; if the second database
   transaction fails, keep writers stopped and rerun the command. Deterministic
   keys make that recovery idempotent and no legacy row is deleted.
6. Create explicit scope mappings for every observed Admins.Core GUID and
   VIPCore `sid`; resolve missing or duplicate mappings before import.
7. Import group definitions with stable UUIDs and legacy portal numeric IDs.
   Preserve original JSON as the starting definition only; future edits write
   canonical arena rows.
8. Populate group/scope availability, then backfill portal listing, reward,
   and catalogue target UUIDs. Compare every listing target before enabling it.
9. Import native Admins.Core/VIPCore assignments and portal overlay
   memberships with provenance. Build a conflict report before choosing a
   current VIP subscription. Do not discard lower-tier or duplicate evidence;
   retain it as superseded/conflict history.
10. Compare legacy and canonical effective access per player and scope. Fix all
   unexplained differences.
11. Deploy arena write APIs and readers, then switch staff management to the
   canonical tables. Keep legacy readers available for an observation window.
12. Deploy the portal saga worker and only then allow new jobs to enter
    `activation_pending`.
13. Enable arena outbox reconciliation for portal badges and inventory group
    rewards. Monitor pending jobs, stale leases, rejected commands, conflicts,
    and unpublished events.
14. Make legacy membership writers read-only. Retire legacy tables only in a
    later, separately approved destructive migration after the rollback window.

For an existing player with multiple active VIP tiers, the import should first
group candidates by player, explicit scope, and VIP family. Prefer an already
recorded successful portal conversion result when it unambiguously names the
effective tier. Otherwise apply the approved tier precedence and expiry policy,
store the chosen row in `arena_vip_subscriptions`, and preserve every other row
as superseded or conflict history. Never hide the player merely because their
memberships span multiple legacy tabs or scopes.

## Rollback and operational rules

These migrations are additive, and existing tables stay intact. Before the new
writer is enabled, rollback is simply returning readers to the legacy sources.
After activation jobs exist, first stop new prepares, drain or reconcile every
non-terminal job from command receipts, and stop outbox delivery before
switching writers. Do not drop canonical tables or change a pending item by
hand as a rollback shortcut.

Production code should expose metrics and alerts for:

- non-terminal jobs older than their expected retry window;
- commands stuck in `received` or `processing`;
- expired rate snapshots that were never applied;
- `manual_review` jobs, subscription conflicts, and hash mismatches;
- stale outbox leases and unpublished events;
- canonical memberships whose group/scope mapping is disabled or missing;
- drift between arena membership `row_version` and portal projections.

All timestamps are UTC `DATETIME(6)`. Services must send UTC values and never
interpret them in the portal or game server's local timezone.
